# Monitor with FALCO

A  monitoring tool using Falco and Python. It detects
suspicious activity—such as unexpected access to the host filesystem—generates
alerts, and automatically isolates the responsible container.

## Architecture

Containers --syscalls--> Falco --rules--> JSON alert
| HTTP (token)
v
Python Service (FastAPI, systemd)
- Correlates with container mounts
- Sends notifications and writes JSON audit logs
- Isolates: cuts network access, pauses the container, and saves a forensic image

Additionally, a thread listens for Docker creation events and inspects the
working directory (addressing the pattern seen in CVE-2024-21626  "Leaky Vessels").

## Repository Structure

install/setup-falco-guard.sh   Automated installation script
rules/host_access.yaml         Falco rules
service/monitor.py             Python service (FastAPI)
service/falco-guard.service    systemd unit file
service/env.example            Configuration template (no actual token included)
tests/run_tests.py             End-to-end tests
tools/check_versions.py        Version inventory (runc/containerd/docker)
tools/scan_workdir.py          Scanner for WORKDIR /proc/.../fd

## Installation
Installation for Debian/Ubuntu distribution
Linux VM (tested on Ubuntu 22.04/24.04/26.04, kernel >= 5.8)
dedicated to this lab environment, isolated from real networks and data. 

git clone <repo-url> falco-guard
cd falco-guard
TOKEN=$(openssl rand -hex 24)
echo "Save this token: $TOKEN"
sudo ./install/setup-falco-guard.sh "$TOKEN"

The script installs Docker and Falco (using the `modern_ebpf` driver), copies the rules,
creates a service user, sets up a Python virtual environment, configures a systemd unit,
and starts the service in `DRY_RUN=true` (simulation) mode.

After installation, log out and log back in (to apply the `docker` group membership) and verify:

curl -s http://127.0.0.1:8080/health

It should return: `{"status":"ok","dry_run":true,"mode":"all"}`.

## How it works

1. Falco flags a potential threat when a container accesses files with sensitive
names (e.g., `shadow`, `sudoers`, SSH keys, etc.), regardless of where they are mounted.
2. The service maps the path as seen inside the container to the actual path on the
host by analyzing its bind mounts.
3. Possible outcomes: the file belongs to the container (`internal-file`), the host path
is non-sensitive (`mount-not-sensitive`), or the host path is sensitive (triggering isolation).
4. Rules tagged with `host_escape` and marked as critical priority (such as accessing
the Docker socket) trigger immediate isolation, bypassing the correlation step.

## What the Isolation stands for

It disconnects all networks, pause the container, and save its
filesystem as a "quarantine" image for forensic analysis. This does not include the
contents of host-mounted volumes.

To release a container after investigation:

docker unpause NAME
docker network connect bridge NAME

An isolated container may have compromised the host; ensure you investigate the
node itself, not just the container. ## Configuration (/etc/falco-guard/env)

GUARD_TOKEN=<token of at least 16 characters, generated by the script>
DRY_RUN=true|false        simulation or actual isolation
ENFORCE_MODE=all|label    "label" isolates only containers with falco-guard.enforce=true
COOLDOWN=300              seconds between actions on the same container

Exceptions: use the label `falco-guard.ignore=true` on the container.
Falco must be configured with `rule_matching: all` and `http_output` pointing to the service
(including the token; see `install/setup-falco-guard.sh`, step 3).

Always start with `DRY_RUN=true`. Only enable active (real) mode after
evaluating false positives in your environment.

## Testing

sudo python3 tests/run_tests.py

(Copy the files to `/opt/falco-guard/` first, or adjust the service paths accordingly.)

Tested on Ubuntu 26.04 (kernel 7.0), Falco 0.45.1, Docker 29.9.2, runc 1.5.2,
and containerd 2.4.2. Results in active isolation mode: 7/7 scenarios handled correctly
(detected three types of mounts—`/host`, full root mounted under a different name,
and `/etc` mounted—; correctly ignored internal files and benign paths;
respected exempted containers; no alerts for legitimate containers).
